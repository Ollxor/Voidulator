# Voidulator — Claude Code Context

## Architecture: intentional single-file design

Everything lives in `index.html` (~6,600 lines). This is not a shortcut — it is the deployment model. The app is meant to be droppable into any static host or opened directly from the filesystem. No build step, no bundler, no npm. Changing to a multi-file structure would break the offline/PWA use case and complicate the zero-dependency guarantee.

Supporting files:
- `manifest.json` — PWA manifest (icons, theme color, display mode)
- `sw.js` — Service worker (**network-first**, cache only as offline fallback — see Deployment)
- `icon.svg` — Source icon (512×512 vector)
- `apple-touch-icon.png` — Generated from icon.svg at 180×180 for iOS home screen

## State object: `S`

The entire application state is a single plain object `S`. Sliders, dropdowns, toggles, and animations all read from and write to `S`. Key sub-trees:

- `S.beams` — beam count, width, colors, per-beam rotation speeds/phases
- `S.segments` — beam-length cycle: `on`, global `wavelength`/`speed`, and `items[]` (each `{w, colInherit, col[3], opacity, soft, driftOn, speed, wavelength}`). Replaced the old `S.pulse` in v1.23; old pulse fields migrate via `readSegments()`
- `S.widthWave` — shape-effect on/off, shape type, density, size, flow, rotation
- `S.trails` — on/off, length, hue shift
- `S.emitters[]` — array of emitter positions and per-emitter state
- `S.scenes[]` — 8 save slots (each is a snapshot of S minus ephemeral state)
- `S.audio` — mic input state, sensitivity, smoothing; `S.audio.bands` (smoothed per-band energy: all/bass/mid/high) and `S.audio.raw` (unsmoothed, feeds the beat detector)
- `S.modRoutes[]` — modulation matrix routes `{source, target, amount, enabled}`
- `S.beat` — beat detector (enabled, envelope `env`, decay, sensitivity, on-beat actions)
- `S.midi` — WebMIDI state (`bindings`: CC key → param id, `noteBeat` flag)
- `S.rec` — video recorder state (active, recorder, chunks, dimensions)
- `S.hueOffset` — runtime-only global hue rotation (degrees), applied to all beam colors in `renderBeamsGL`; driven by the matrix and beat hue-jumps, never persisted

`S` is serialized to `localStorage` on change (debounced 2 s, skipped when tab is hidden, flushed on `pagehide`). Factory-reset restores hardcoded defaults including 15 curated scenes.

## Parameter registry & modulation matrix

`MOD_PARAMS` is the single registry of programmatically drivable parameters (`{label, get, set, min, max(), range(), wrap?}`). Three systems plug into it — **add new modulatable parameters here, never as one-off switch statements**:

1. **Modulation matrix** (`applyModulation`/`restoreModulation`): routes in `S.modRoutes` add `source × amount × range` to each target. **Non-destructive** — base values are snapshotted into `modBase` before render and restored after (`restoreModulation` runs at the end of `loop()`), so sliders, autosave, and scenes only ever see unmodulated values. Sources: `all`/`bass`/`mid`/`high` (smoothed band energies) and `beat` (the beat envelope). Amounts are bipolar (−1…+1).
2. **MIDI CC bindings**: map a knob absolutely onto min→max of a registry param. CCs set *base* values (events arrive between frames, when bases are restored), so matrix modulation stacks on top.
3. **Beat actions** read/write state directly (`triggerBeatActions`: ripple spawn, hue jump).

Matrix routes + beat settings persist in `localStorage['voidulator-mod']` (global rig config, deliberately **not** per-scene — scenes are visual compositions, the matrix is the performance rig). They are also included in JSON preset export/import. MIDI bindings persist separately in `localStorage['voidulator-midi']`.

## Wave field (FDTD simulation)

`S.field` is a fourth emission mode (Emission select → "Wave field"), mutually exclusive with beams/rings. `renderBeamsGL` early-returns to `renderField()` when `S.field.enabled`. It's a real finite-difference wave-equation solver on the GPU:

- **Float ping-pong**: two RGBA16F textures (`fieldTex[0/1]`), each texel storing `(u_n in .r, u_{n-1} in .g)`. Needs `EXT_color_buffer_float` (`fieldFloatOK`); without it `renderFieldUnsupported()` shows a notice.
- **`waveProg`** (update): `u_{n+1} = 2u_n − u_{n−1} + C²·∇²u_n` with a 5-point Laplacian; `C = S.field.speed` must stay < 0.707 (2D stability). Out-of-room neighbours (mask < 0.5) mirror the centre value → **Neumann reflecting walls**; in absorb mode they read 0. Sources injected as gaussian bumps at emitter UVs; `S.field.substeps` passes per frame.
- **Mask**: `buildFieldMask()` rasterizes the current room (circle/polygon/bent/ellipse/parabola — uses `S.vertices`/`S.circle`) into a square texture via the 2D canvas, keyed on geometry so it rebuilds only on change. `fieldMaskMap` stores the px→grid-UV transform; `fieldPxToUV()` maps emitter/click positions in.
- **`waveColorProg`** (colorize): soft tone-map `1−exp(−|u|·gain)` (never harsh-clips a resonating cavity) → spectral/bipolar/mono, into `sceneTex`, then the existing `runBloom`/`compositeWithBloom`.
- Source phase advances in `loopBody` (`S.field.phase`); the FDTD itself is dt-independent (fixed C, fixed substeps). Click-on-stage and the Pulse button push one-shot `fieldImpulses`.
- Inspired by Nils Berglund's wave sims (CC0); this is independent code. Defaults (damping 0.02, amp 0.4, gain 2.5) give clean travelling fronts rather than a saturated standing wave.
- **Aspect handling**: the field grid is square; the colorize pass renders into a *centred square viewport* (`vx,vy,sq` from `fieldMaskMap × dpr`, GL bottom-left origin) on the otherwise-cleared scene target — never stretch the square field across a non-square canvas, or circular waves become ellipses on mobile.
- **Waveform** (`S.field.waveform`): `continuous` (steady sine), `rings` (sine × a per-period gaussian burst window at `pulseRate`, `pulseWidth` sets sharpness → distinct expanding rings), or `off` (manual impulses only). Phases (`phase`, `pulsePhase`) advance in `loopBody`.
- Field has its own draggable wave-source emitters (`S.field.emittersNorm`, magenta) with the shared formation helpers (`arrangeFormationGeometric`/`centerFormation`/`uprightFormation`/`setFormationCount`, `defaultFormationRadius` spreads a collapsed formation).
- **Room boundary (v1.28, fixed a real bug): drawn ONLY as the fading-amber edit flash, never at rest.** Editing Shape/Eccentricity/Wall bend calls `flashRoomOutline()` → `roomOutlineUntil`; `drawOverlay` draws the boundary in fading amber while `flashLeft > 0` and draws **nothing** otherwise — do not reintroduce a "resting" stroke, not even black. The `#overlay` 2D canvas is layered on top of `#gl` via CSS and is never touched by the kaleidoscope fold shader, so any resting stroke is static in room-space while the WebGL pattern (beam rotation, kaleidoscope, trail feedback) moves underneath it — a fixed line sitting where a rotating bright pattern periodically sweeps past reads as a stray line slicing across the animation, worse the denser the pattern (Kaleidoscope, Wave field). This is not fixable by choosing a better resting color; a truly invisible line doesn't exist once the pattern itself gets bright near the edge. If a resting boundary indicator is wanted again, it must be something that reacts to what's under it (e.g. XOR/difference compositing), not a fixed color — a plain stroke reintroduces this exact bug.

## Bloom (Glow) pipeline

`S.bloom = {enabled, strength, threshold}`, persisted per-scene (lerped in transitions) and in presets. GL flow in `renderBeamsGL`:

- **No-trails path**: beams render into `sceneFBO` (full res) instead of the screen, then `runBloom(sceneTex)` → `compositeWithBloom(sceneTex)`.
- **Trails path**: the existing trail composite texture (`writeTex`) is the bloom source; the final screen copy is replaced by `compositeWithBloom(writeTex)`.
- `runBloom`: bright-pass (smooth knee above `threshold`) into a **quarter-res** target, then separable 9-tap gaussian (H then V, taps 1.5 texels apart). Result lands in `bloomTexA`.
- `compositeWithBloom`: blit scene (blend off), then additive blit of `bloomTexA × strength` — **must explicitly set `gl.blendEquation(gl.FUNC_ADD)` before `gl.blendFunc(gl.ONE, gl.ONE)`** (not just the func), since `S.blendMode` can leave `MAX`/`FUNC_REVERSE_SUBTRACT` active (Lighten/Difference — see Blend modes below); the glow layer must always be plain additive regardless. Then `setBlendMode(S.blendMode)` to restore the state beams expect.
- `drawPostQuad` **disables the beam vertex attribs first** — leaving them enabled while pointing into a smaller/empty vertex buffer makes the fullscreen draw `INVALID_OPERATION`.
- All render targets resize lazily by checking `tex._w/_h` against the canvas (same pattern as trails), so recording's resolution switch just works.

## Overlap only (`S.overlap = {enabled, minCount}`, v1.35)

Hides everything except pixels where `minCount`+ beams/rings overlap. A genuine second render pass, not a colour/blend trick — **no-trails path only**; the toggle is visible but a no-op while Trails is on (see below for why).

- **Coverage counting**: `drawCoverageGeometry()` redraws the SAME range `drawBeamGeometry()` just drew (beams+rings+phosphor, one `vertBuf`) into `coverageFBO`, using `coverageProg` — a trivial shader (`coverageVs`/`coverageFs`) that ignores colour/segments/glow entirely and outputs a flat `1.0/64.0` per fragment with additive blending (`ONE,ONE`/`FUNC_ADD`). **The `/64` matters**: `coverageTex` is a standard UNORM8 target (`makeRenderTarget`, same as everything else in this pipeline) — plain additive blending on an 8-bit channel clamps at 1.0, so a naive `+1.0` per shape could never distinguish 2 overlapping shapes from 1. Scaling each contribution down to `1/64` keeps counts up to 64 resolvable (`64 × 1/64 = 1.0`, exactly where an 8-bit channel runs out of headroom anyway) without needing a float render target (`EXT_color_buffer_float`, gated/unsupported on some devices — see the wave field's `fieldFloatOK`) for what only ever needs a small integer.
- **Masking**: `applyOverlapMask(srcTex)` runs the coverage pass above, then blits `srcTex` through `overlapMaskProg` into `overlapMaskTex`: `count = texture(u_coverage,uv).r * 64.0; if (count < u_minCount - 0.5) → black; else → srcTex`'s colour unchanged. Returns `overlapMaskTex`.
- **Where it plugs in**: `renderBeamsGL`'s no-trails branch extends its existing "does this need `sceneFBO`" check (`useBloom || useKscope`) to also force the FBO route when `S.overlap.enabled`, then right after the normal (unmodified) beam draw computes `const sceneSource = useOverlap ? applyOverlapMask(sceneTex) : sceneTex;` and uses `sceneSource` everywhere `sceneTex` used to be read (into `runBloom`/`compositeWithBloom`, or the plain kaleido/overlap blit-to-screen branch, now taken whenever `useKscope || useOverlap`). Masking happens on the **fresh beam draw**, before Bloom/Kaleidoscope ever see it — so neither needs to know Overlap exists: Bloom glows only the surviving (already-masked) regions, and Kaleidoscope's `kfold()` folds the already-masked result exactly like it folds everything else. When `useOverlap` is false, `sceneSource === sceneTex` (same reference) — the whole downstream path is byte-identical to before this feature existed.
- **Why Trails isn't supported yet**: the trails path draws fresh beams directly into `writeFBO`, blended on top of the already-blitted faded history in the same step — there's no separate "just this frame's beam pixels" texture to run `applyOverlapMask` against without first splitting that draw into "beams → scratch target → mask → composite onto `writeFBO`", mirroring how the existing Trail-brightness feature (`dimTrails` branch, same function) already draws beams into more than one target when it needs to. Doable, just not done — a natural follow-up, not attempted here. Re-confirmed still true in v1.42 (a report of "Overlap only does nothing" turned out to be exactly this, encountered by a user who had Trails on): fully motion-frozen A/B across every `minCount` produced byte-identical render hashes on/off, matching the code-level reasoning above rather than contradicting it.
- Uses its own vertex attribute setup (`coverageProg`'s own `a_pos` location, looked up via `gl.getAttribLocation` — **not** the cached `a_pos`/`a_t`/`a_col`/`a_alpha`/`a_edge` globals, which are `prog`'s attribute indices and aren't guaranteed to mean anything for a different linked program) — those beam-program attribs are explicitly disabled first, same defensive pattern `drawPostQuad` already uses when switching programs mid-frame.

## Kaleidoscope, Generative gallery, Vesica & trail controls (v1.16–1.19)

- **Kaleidoscope** (`S.kaleido {enabled, segments, rot, spin, mirror}`): a `kfold(uv)` GLSL snippet shared by BOTH final-blit shaders (`copyFs`/`blitFs`) — the fold lives in the existing last-pass programs rather than a new pass, so every render path (trails/field/generative × bloom on/off) gets it without duplicated pipeline logic. `uploadKscopeUniforms(prog)` must be called at every final-blit program bind (uniforms persist per program, so all sites re-set them each frame). The no-trails+bloom-off beam path routes through `sceneFBO`+`copyProg` only when kaleido needs it. `rot` advances by `spin` in `loopBody`; `kaleidoRot` is a `MOD_PARAMS` target (wrap).
- **Generative** (`S.generative {enabled, style, speed, scale, hue}`): fifth emission mode, mutually exclusive like the field — `renderBeamsGL` early-returns to `renderGenerative()` BEFORE the field check. `GEN_PROGS` registry maps `style` → program (aurora/tunnel/orbs, all original shaders sharing a cosine-palette uniform block; licensing reasoning in RESEARCH.md §22). Renders a fullscreen quad into `sceneTex` via `ensureBloomTargets()` → same bloom/kaleido tail as everything else. **To add a gallery style:** write a fragment shader on `copyVs`, register in `GEN_PROGS`, add the `<option>` + a translated label — nothing else. Emitter dots are hidden in this mode (`drawOverlay` gate).
- **Vesica piscis** (`polygonType 'vesica'`): two R-circles with centre separation R, √3∶1 lens. `S.vertices` still holds the 258-point traced polyline (drawn boundary, wave-field mask, centroid — all generic over `S.vertices`), but collision is analytic: `S.wallArcs` holds the two exact circles (`{line:false, cx, cy, R, apexAng: 0|π, halfSpan: π/3}`), so `computePath`'s `const arcs = S.isCircle ? null : S.wallArcs` picks them up automatically — same `firstHitArcs`/`arcNormal` path as bent polygons, no other code changes. **This matters**: the segment-approximation this replaced (v1.28 and earlier) was a real bug — reflecting off the wrong one of 258 near-identical tiny segments near a cusp sent beams on wildly wrong paths ("very long steps" a couple of bounces later, fixed in v1.29). Do not revert Vesica to `firstHitPoly`/`findNearestEdge` collision. Generating centres stored in `S.foci` (reuses the ellipse focus markers). Wall bend exempt (no `baseVertices`) — `bendWalls()` already no-ops here (`if (S.isCircle || !S.baseVertices) return;`), so it can't clobber `S.wallArcs`.
- **Trail filter, cutoff & brightness** (`S.trails.filter 'smooth'|'crisp'`, `S.trails.cutoff` 0–0.06, `S.trails.opacity` 0–1): `applyTrailFilter()` lazily re-stamps LINEAR/NEAREST on both ping-pong textures (reset to null on `ensureTrailFBO` recreate — fresh textures are LINEAR); `cutoff` feeds the trail shader's `u_threshold` residue floor. These are the user-facing dials for the sub-pixel moiré/interference look (thin beams + slow speed + long trails). `opacity` ("Brightness", v1.27) dims the accumulated trail independently of decay rate — see the dedicated writeup under "Trail ping-pong" below for why that needed a second beam draw rather than just scaling the feedback.

## Smooth randomness: `smoothNoise()`, Wander, Drift motion (v1.40)

`hash01`/`valueNoise1`/`smoothNoise` are a small deterministic value-noise generator (two octaves weighted 0.65/0.35 so the output stays in [0,1)). Deterministic in the phase, so nothing needs per-frame state beyond an advancing `t`. Two consumers:

- **`wander` modulation source** (`S.wander = {rate, t}`), listed in `MOD_SOURCES` next to LFO 1/2 and evaluated in `applyModulation`'s `src` map. **`S.wander.t` is deliberately NOT wrapped to a period** — it's noise, not a cycle, and wrapping would reintroduce the looping the source exists to avoid (it's bounded at 100000 only to protect float precision). Rate persists in the rig config (`saveModConfig`).
- **Trail drift motion** (`S.trails.driftMode` `'off'|'orbit'|'wander'`, plus `driftRate`/`driftAmount`, and runtime `driftAngle`/`driftPhase`). `updateTrailDrift()` writes `fbDriftX/Y`.

### Drift motion is a dot on an X/Y pad (v1.41)
`updateTrailDrift` maintains `driftPX/driftPY` — a position on a normalised `[-1,1]` pad — and outputs `fbDriftX/Y = pos * driftAmount`. **Why the pad, and not (as v1.40 had it) just an angle at fixed radius:** with Zoom on, the feedback transform's fixed point — the tunnel's vanishing point — sits at `uv = 0.5 - drift/fbZoom`. The drift vector is therefore a *position control for the tunnel*, and moving the dot around the pad flies the tunnel around the screen. (At `fbZoom == 0` there's no tunnel and drift is a plain translation.) Useful when reasoning about ranges: at `fbZoom -0.042` and `driftAmount 0.0085`, the vanishing point swings about ±0.2 of the screen.

Modes:
- `'orbit'` — angle advances, radius pinned at 1 (rides the rim).
- `'wander'` — steered particle. The noise drives the **turn rate**, not the heading: that is what produces a smooth turn radius (the dot arcs into a new direction rather than snapping), and driving the heading directly would also confine it to the noise's bounded range instead of letting it go anywhere. Speed is modulated by a second, decorrelated noise stream so it accelerates and coasts. Containment is a gradual steer toward centre past `DRIFT_RIM`, **not** a bounce — a bounce would put a hard corner in the path, defeating the smooth turn radius. A hard clamp remains as a backstop only.
- `'shape'` — walks the perimeter of an N-gon (`driftSides`, 2–12) interpolating along each edge, with the polygon slowly self-rotating. Correctness is easy to check from the traced radius range: it should span the polygon's apothem to 1 (hexagon `cos30 = 0.866`, triangle `cos60 = 0.5`, `sides=2` passes through 0).

`dtSec` is clamped inside this function: a tab-restore frame spike must not teleport the dot across the pad.

### Ordering: it must run before `applyModulation()`
`updateTrailDrift(dtSec)` is called in `loopBody` immediately **before** `applyModulation()`, so the driven value becomes the base that matrix routes add to (and that `restoreModulation()` restores at end of frame). Move it after and `restoreModulation` would write back a stale base, with the two systems fighting over `fbDriftX/Y`.

**Testing note:** modulation is non-destructive — `restoreModulation()` runs at the end of every frame, so reading `S.*` after `Voidulator.step()` gives the *unmodulated* base and a naive test concludes a route "does nothing". Capture during the frame instead, e.g. by temporarily wrapping `Voidulator.MOD_PARAMS[target].set`. That setter fires twice per frame (apply, then restore), so consecutive samples alternate — don't compute frame-to-frame smoothness from that series.

## Audio analysis & beat detection

### The `raw` vs `bands` split — do not collapse it (v1.38)

`updateAudio()` produces **two different signals per band, and mixing them up is what broke beat detection for several versions:**
- `S.audio.raw[band]` — **true acoustic energy, deliberately NOT multiplied by `S.audio.sensitivity` and NOT clamped.** Anything reasoning about *dynamics* must read this.
- `S.audio.bands[band]` — smoothed, sensitivity-scaled, soft-saturated 0–1. This is the display meter and the modulation-matrix source, where a bounded 0–1 is what's wanted.
- `S.audio.kick` — the narrow `KICK_HZ` (40–120 Hz) band, unscaled. The beat detector's actual input.

The bug: `raw` used to be `Math.min(energy * sensitivity, 1)`, and the beat detector read `raw.bass`. At the old default sensitivity of 4, normal music pinned it at exactly 1.0 (measured: 100% clipped, sd = 0). An adaptive threshold looking for a spike above a rolling mean finds nothing in a constant signal, so **beat detection never fired at the default setting** — and raising Sensitivity, the intuitive fix, made it worse. If you ever find yourself scaling `raw` by sensitivity again, this is what you are re-breaking.

`softKnee()` (linear below 0.7, easing asymptotically to 1.0 above, with matching derivative at the knee) replaced the hard clamp on `bands`, so a high Sensitivity now compresses instead of flattening the modulation sources.

### Auto gain (v1.39)
`S.audio.autoGain` derives the gain from a rolling loudness estimate (`agcPeak`, fast ~0.15 s attack / slow ~6 s release) instead of the Sensitivity slider, targeting `AGC_TARGET` (0.8, not 1.0, so peaks still have somewhere to move). It **replaces** Sensitivity rather than multiplying with it, and the slider greys out (`.ctrl-disabled`) so it doesn't look live but inert. `agcPeak` has a hard floor — without it, silence drives the estimate toward zero and the gain toward infinity, so the first sound after a pause would slam to full scale. Auto gain only affects `bands` (meters + modulation), never `raw`/`kick`, so beat detection is identical with it on or off.

### Rig config must load BEFORE any preset (v1.39)
`loadModConfig()` is called *before* the URL/autosave/startup-preset block in `init()`, not after. `applyPreset()` calls `saveModConfig()` whenever the payload carries routes or beat settings — if the rig config hasn't been read yet, that write persists the still-default values over the stored ones, and the subsequent load reads back what was just clobbered. This silently discarded saved audio calibration (and would do the same to matrix/beat settings). Don't move that call back down.

### Band edges are Hz, not bin fractions
`BANDS_HZ` / `KICK_HZ` declare real frequencies; `ensureBandBins()` resolves them to bin indices from the live `ctx.sampleRate` and `analyser.fftSize` (cached on `A.binKey`). The old code sliced the bin array by percentage, which meant the bands drifted with sample rate and fftSize — at `fftSize` 128 each bin spanned ~375 Hz and "bass" actually meant 0–3.4 kHz, so snares and vocals swamped the kick. **`fftSize` is 2048** (~23 Hz bins) for that reason; `smoothingTimeConstant` stays **0** because the analyser must not smear transients before the detector sees them (per-band smoothing happens afterwards in `updateAudio`).

### Detector
`updateBeat(dtSec)`: a beat fires when `S.audio.kick` exceeds its ~0.7 s rolling mean × `S.beat.sensitivity`, gated by a 0.18 s re-trigger interval and a 0.05 absolute floor. **The mean is computed over preceding frames only** — the current sample is pushed into `hist` *after* the comparison, because including it let a loud transient inflate the very average it was being tested against. On detect: `S.beat.env = 1` (decays as `exp(-decay·dt)`, usable as a matrix source) and `triggerBeatActions()` fires the enabled one-shots. MIDI note-on can fire the same path when `S.midi.noteBeat` is on.

### Testing this without a microphone
`getUserMedia` isn't available headless, but the calibration lives above the mic: stub `S.audio.analyser` with an object exposing `fftSize`, `frequencyBinCount` and `getByteFrequencyData(arr)` that writes a synthetic spectrum, set `S.audio.ctx = {sampleRate}` and `S.audio.active = true`, then drive `Voidulator.step()`. That exercises the real band-splitting and the real detector. Measured behaviour to regress against (synthetic 128 BPM techno, 20 s, 43 kicks): full detection at every Sensitivity 0.5–5; Beat Sensitivity usable across 1.05–1.8 and dropping beats from 2.0; correct at 100–174 BPM; zero false positives on silence or a sustained transient-free tone; and no double-triggering with a snare on 2 and 4. **Warm up ~40 frames before counting** — the first `step()` call's `dt` depends on real page-load time and will otherwise shift results run to run.

## Video recording

`startRecording()` overrides the device pixel ratio (`recDprOverride` in `resize()`) so the GL canvas backing store renders **natively** at the chosen height (480/720/1080/2160) — geometry is unaffected because the room works in CSS-pixel space via `S.dpr`. Width follows the window aspect (rounded to even for the encoder). Each frame `captureRecFrame()` composites `#gl` + `#overlay` into an offscreen canvas whose `captureStream(60)` feeds `MediaRecorder` (VP9 → VP8 → WebM fallback; bitrate scales 8–45 Mbps with resolution). Stop downloads a `.webm`. Recording auto-stops when the tab is hidden (the render loop is the frame source). Trail framebuffers re-size automatically on the resolution switch (dimension check in the FBO setup).

## Debug handle

`window.Voidulator` exposes `{S, MOD_PARAMS, triggerBeatActions, startRecording, stopRecording, renderModRoutes, syncBeatUI, onMidiMessage, renderMidiBindings}` for console debugging and testing without hardware — e.g. `Voidulator.S.beat.env = 1` simulates a beat, `Voidulator.onMidiMessage({data:[0xB0, 21, 64]})` simulates a CC message.

## Render pipeline

```
requestAnimationFrame
  → update physics (emitter rotation, segment scroll, audio level)
  → trace rays (WebGL vertex buffer: one call per bounce layer)
  → composite trails (ping-pong framebuffer)
  → draw overlay (2D canvas: emitter dots, drag handles)
```

The WebGL canvas (`#gl`) and the 2D overlay canvas (`#overlay`) are stacked absolutely inside `.stage`. The render loop pauses when the tab is hidden (`visibilitychange`) and resumes cleanly. `dt` is clamped to 100 ms to prevent jumps on tab restore.

### Vertex buffer
Beam geometry writes into a persistent, growable `Float32Array` (`vertBuf`) rather than allocating per frame. When the required size exceeds the allocated size, the buffer doubles.

### Per-segment allocation (v1.37)
The two largest sources of short-lived garbage were both per-segment (~670 segments/frame at max settings, so ~40k objects/second each), and both are gone. **No frame-time figure is claimed** — see the benchmarking note at the end of this section; the justification here is the removed allocations, which are a property of the code, not a measurement.
- **`computePath` pushes `from: o`, not `from: {...o}`.** `o` is already a private clone made at function entry and is only ever *reassigned* in the loop, never mutated in place, so the defensive copy allocated a second object per segment for nothing. **If anything ever starts mutating `o` in place, restore the spread** — ring ray caches hold these segment objects across frames, so an in-place mutation would silently change already-cached geometry under the renderer.
- **Depth-mode sort staging is pooled** (`depthSegPool` owns the objects and only grows; `depthSegView` holds the references that actually get sorted, with `depthSegView.length = nItems` each frame to drop leftovers from a busier previous frame). Sorting shuffles the view, never the pool, so the pool's index→object mapping stays stable.

Both were verified bit-identical against the previous build across beams in four room shapes plus spinning rings, and the pooling additionally against a segment count swung 672 → 28 → 672 repeatedly (the case where a stale-reference bug would show). When A/B-testing rendering this way, **give each page its own browser context and clear `localStorage` first** — the app autosaves, so two pages sharing an origin start from different state and the comparison silently becomes meaningless (a control run comparing a build against *itself* is the cheap way to confirm the harness is sound before trusting a result).

**Benchmarking caveat — do not trust frame timings from the headless SwiftShader setup.** Measuring this change produced, on the same build, medians of 27 ms, 2.8 ms and 0.5 ms across three sequential runs, and individual samples inside a single run spanning 3.7 ms → 205 ms. Switching to paired/interleaved sampling (both builds loaded at once, measured round-robin so load drift hits both) did not rescue it: the optimised build won only 9 of 15 paired rounds, which is chance. Two earlier sequential runs suggesting "~58–61% faster" and a paired run suggesting "53.9%" are all inside that noise and none of them are quotable. If a real number is ever needed, measure on an idle machine with hardware GL — or better, count allocations directly rather than timing them. What *is* solid here is the mechanical claim: two objects per segment are no longer allocated, and the rendered output is unchanged.

### Trail ping-pong
Two framebuffers alternate each frame. The previous frame is re-drawn faded (`trailFs`), then the new beams draw on top. Key details:
- **Length → fade** (in the trail render block): `fadeRate = 0.995 * pow((len-1)/179, 0.5)`, so **len=1 → fade 0** (previous frame fully cleared = identical to trails Off) up to ~0.995 at len=180. Do NOT reintroduce a non-zero floor — that's exactly the "minimum still smears" bug fixed in v1.24.
- **Feedback (v1.24–1.25):** `S.trails.fbZoom`/`fbSpin`/`fbDriftX`/`fbDriftY` re-sample the previous frame scaled (`u_fbScale = 1 - fbZoom`) + rotated (`u_fbAngle`, radians) + shifted (`u_fbDrift`, UV/frame) about the centre before fading, turning trails into tunnels/spirals/wind-blown streaks. Sampling at `v_uv - drift` (not `+`) is what makes the *content* appear to move by `+drift` each frame — don't flip that sign. The transform is skipped when scale==1, angle==0 and drift==(0,0), so plain trails are byte-identical to before; out-of-frame samples return black. `trailZoom`/`trailSpin`/`trailDriftX`/`trailDriftY` are `MOD_PARAMS` targets. Trails only run in beam/ring/field modes (square stage), so no aspect correction is needed.
- **Beat echo (v1.25):** `S.trails.beatEcho` (0..1) pushes the trail's effective fade toward a near-freeze in proportion to `S.beat.env`: `effectiveFade = fadeRate + (1-fadeRate) * beatEcho * S.beat.env`. `S.beat.env` already decays every frame regardless of `S.beat.enabled` (see `updateBeat()`) and only ever gets set to 1 by real beat detection, so gating on `beatEcho > 0` alone is sufficient — no extra "is beat detection still on" check needed, and no separate framebuffer: it's a pure fade-rate modulation on the existing ping-pong path.
- **Trail brightness (`S.trails.opacity`, v1.27).** Dims the accumulated trail *without* touching its decay rate. Multiplying the feedback would be mathematically identical to lowering Length, so instead: when `opacity < 1`, the faded history is blitted into `sceneFBO` at `opacity` **before** the beams are drawn (that ordering matters — `writeTex` only holds history-only at that point), the beams are then drawn into `writeFBO` unweighted for next frame's feedback, and drawn a *second* time into `sceneFBO` at full strength; `sceneTex` becomes the display source. Costs one extra fullscreen blit + one extra beam draw, so it is gated behind `opacity < 0.999` and `opacity == 1` runs the original single-draw path untouched (verified pixel-identical). The second beam draw **must** re-call `uploadBeamUniforms()`: `drawBeamGeometry()` zeroes `u_segOn`/`u_edgeIntensity` for its phosphor pass and never restores them, so a second draw without it silently loses segments and edge softness.
- **Wall handling (`S.trails.wallMode`: `'off'|'clip'|'reflect'`, v1.32 clip, v1.34 reflect).** The Feedback transform above is a pure UV scale/rotate/shift with no concept of the room shape. The original bug (`'off'`): a sustained zoom pulls trail content out to ever-larger radii, and since `kfold()` (Kaleidoscope fold, above) preserves radius-from-centre and only folds angle, escaped content folds straight back into the visible pattern instead of vanishing off-frame. Root cause turned out to be about **output** position, not sample position: for a convex room, shrinking any interior point toward an interior centre point (which is what positive zoom's sampling does) is provably still interior, so the escape was never about the transformed sample crossing the wall — it was about output pixels *outside* the room still displaying a magnified view of interior content, because nothing stopped them from sampling at all. Both `'clip'` and `'reflect'` fix this the same way at the top of `trailFs`: force output pixels outside `u_wallMask` to black, unconditionally, every frame, *before* computing the feedback-transformed sample — this also scrubs anything already-escaped in the history buffer, not just new leakage.
  - **`'clip'`**: that output-position check is the entire fix. `buildTrailMask()` rasterizes the room shape (circle or polygon, via `S.isCircle`/`S.circle`/`S.vertices` — same technique as `buildFieldMask()`, framed directly in the trail buffer's own square-canvas UV space since `buildShape()` always centres the room at `(W/2,H/2)` with a fixed margin, no padding/centroid remap needed) into `trailMaskTex`, cached on a geometry key like the field mask.
  - **`'reflect'`**: additionally reflects the feedback-transformed *sample* position across the nearest wall when it lands outside the mask (up to 2 passes — a single reflection can undershoot near concave walls), instead of leaving it to sample garbage or clipping it. `buildTrailWallField()` computes a second texture (`trailWallFieldTex`, RG = nearest boundary point in UV space, BA = wall normal packed `*0.5+0.5`) — circles get an exact analytic point+normal; every other shape reuses the same nearest-point-on-polyline approach `findNearestEdge()` already uses for beam collision fallback, strided down to ≤64 segments since dense traces (blob: 720 points) would make the O(res²×segments) search slow (a coarser boundary here is imperceptible for this stylized bounce). The shader reflection `uv - 2*dot(uv-B,N)*N` is sign-independent in N, exactly like `reflectByNormal` already relies on for beam walls (`arcNormal`/the raw `(-e.y,e.x)` perpendicular in `computePath`'s polygon fallback) — so the field doesn't need to work out which way is "outward," any consistent perpendicular works. **This is an approximation, not a true multi-bounce raycast** — a real bounce needs the incoming ray direction, which a pixel's position alone doesn't carry — most accurate on simple/convex rooms.
  - **Both `trailMaskTex` and `trailWallFieldTex` always exist** (a cheap 1×1 dummy — white/"inside" for the mask, mid-grey/no-op-normal for the field — created on first call regardless of mode) so the per-frame draw can unconditionally bind both texture units and set both sampler uniforms without ever leaving one pointed at an unbound/stale texture; each build function internally no-ops past the dummy-creation step when the current `wallMode` doesn't need it. `buildTrailMask()`/`buildTrailWallField()` are both called unconditionally every frame trails render (not gated at the call site) — the mode-check lives inside each function, mirroring `buildFieldMask()`'s own pattern of a cheap per-frame call gated by an internal cache key.
  - Old scenes/presets only have the v1.32 boolean `S.trails.containWalls`; `readTrailWallMode(trailsSrc)` migrates it (`true`→`'clip'`) the same way `readSegments()` migrates the old `S.pulse` shape. Off by default; existing scenes render unchanged.

### Trail Smoothness / Style / Hue shift+Saturation lifetime model (v1.42)

**The bug this fixes wasn't a bug**, it was a resolution ceiling: the trails path stamps exactly one full-strength beam per rendered frame, and Length only controls how many of those stamps survive the fade before `Cutoff` — never how finely spaced in time/angle they are. Anything rotating fast enough relative to the frame rate reads as discrete copies, not a gradient, no matter what Length is set to.

- **`S.trails.substeps` (1–4, "Smoothness")** re-traces the beam path at N angles interpolated across the current frame and stamps each at `1/N` intensity. Implementation split:
  - **`buildBeamsOnly(timeSec, angleDeg, stampMul, depositPhosphor)`** — the old per-frame beam loop (bounce-trace every beam, sort, `pushQuad`) extracted verbatim out of `renderBeamsGL`, now parameterized: `angleDeg` overrides `S.angleDeg` (lets a substep use an interpolated angle instead of the current one), `stampMul` scales every pushed quad's alpha (so N stamps sum to roughly what one did), `depositPhosphor` gates the phosphor-deposit side effect so it only fires once per rendered frame regardless of N. Rings are built separately in `renderBeamsGL` (`buildRingGeometry()`, unaffected by substeps — re-tracing rings per substep would double-count their brightness since, unlike beams, their geometry doesn't depend on the interpolated angle).
  - **`stampBeamsInto(fbo, w, h, stride, timeSec, refVertCount)`** replaces the old inline "draw current beams on top" block, called once per target (`writeFBO`, and again into `sceneFBO` when `dimTrails` is active — see Trail brightness above). At `substeps<=1` or when nothing rotated this frame (`lastAngleDelta === 0`, a module-level var `loopBody` sets from `S.rotationSpeed * dtSec` right before advancing `S.angleDeg`) it's exactly the original single `drawBeamGeometry()` call — **verified byte-identical**: a frozen (non-rotating) scene produces the same pixel hash at every Smoothness value 1–4. Above that, it draws rings + phosphor once each (from the reference build already sitting in `buf` — `refVertCount`/`lastRingVertEnd` mark those ranges, captured *before* the substep loop starts overwriting `vertCount`), then loops N times: truncate `vertCount` back to `lastRingVertEnd`, call `buildBeamsOnly` at the interpolated angle, re-upload, draw just that range.
  - **Only `S.angleDeg` (global rotation) is interpolated** — not emitter spin, LFOs, per-beam speed patterns, or width wave. Scoped deliberately, same spirit as Overlap+Trails below: this is the dominant "tunnel spins, trail looks stepped" case from actual use, and re-tracing every other motion source per substep would multiply `computePath` cost for comparatively little of this benefit. Real cost is up to Nx the per-frame beam-path trace, so it's opt-in and capped at 4x (1x is free — same code path as before this feature existed).
  - `drawBeamGeometry()`'s phosphor sub-pass zeros `u_segOn`/`u_edgeIntensity`/`u_coreIntensity` and never restores them (see Beam glow below) — `stampBeamsInto` re-calls `uploadBeamUniforms()` after its own phosphor draw for the same reason, before starting the beam substeps.

- **`S.trails.style` (`'full'|'edge'|'core'`)** masks what gets fed into the trail accumulator, via a new `u_trailStyle` uniform on the *beam* shader (`prog`, not the trail resample shader `trailFs` — by the time a pixel reaches `trailFs` it's flat RGB, the per-fragment beam-shape info is long gone). Reuses the same `d = abs(v_edge)` cross-beam coordinate Beam glow already computes: edge keeps a thin band near `d=1` (`smoothstep(0.55, 0.95, d)`), core keeps one near `d=0` (`1.0 - smoothstep(0.0, 0.35, d)`). Set in `uploadBeamUniforms()` gated on `S.trails.enabled` — **inert whenever Trails is off**, so the room's normal beam render never changes shape regardless of what Style is set to. This also means Style reshapes the *current frame's* beam too, not just what accumulates into history — there's no separate "what you see" vs "what gets remembered" pass in this architecture (`writeFBO` = history + this frame's beams, one texture), so a clean split wasn't possible without a bigger rearchitect; scoped as "Style only does anything while Trails is on" instead.

- **Hue shift / Saturation are now lifetime-total, not a flat per-frame rate.** The old formula was `hueShiftPerFrame = hueShift / (Length * 2)` — a flat approximation disconnected from how fast the trail *actually* decays, so the same slider value produced very different total rotation depending on Length, and brighter pixels (surviving more frames before `Cutoff`) rotated further than dim ones in the same trail. Fixed by deriving an estimated lifetime-in-frames from the real fade curve and solving for the rate that makes the total come out to the slider value:
  ```
  effCutoff = max(threshold, 0.0008)          // floored so Cutoff=0 doesn't make lifetime infinite
  lifetimeFrames = log(effCutoff) / log(fadeRate)   // fadeRate^k == effCutoff, solved for k
  hueShiftPerFrame = S.trails.hueShift / max(1, lifetimeFrames)
  satShiftPerFrame = S.trails.satShift / max(1, lifetimeFrames)
  ```
  `hueShiftPerFrame * lifetimeFrames` collapses back to exactly `S.trails.hueShift` by construction — **verified algebraically** across Length 1–180 and Cutoff 0–0.06 (includes the len=1 edge case, where `fadeRate≈0` short-circuits to `lifetimeFrames=1` rather than dividing by `log(0)`). 360° now reliably means one full hue revolution by the time a pixel fades out, at any Length/Cutoff — not "roughly half the slider value, more for bright pixels than dim ones," which is what it meant before. **Saturation** (`S.trails.satShift`, new, −1..+1) is the same model applied to HSV saturation instead of hue: negative fades a trail toward gray as it ages, positive pushes toward neon. Both share one `if (u_hueShift > 0.001 || abs(u_satShift) > 0.001)` HSV round-trip in `trailFs` (`hsv.x = fract(hsv.x + u_hueShift)`, `hsv.y = clamp(hsv.y + u_satShift, 0, 1)`) — saturation needs the explicit clamp since, unlike hue, it doesn't wrap.
  - **Testing gotcha hit while verifying this:** summing per-channel pixel values (`rSum`/`gSum`/`bSum`) across a busy multi-beam rotating scene to check hue diversity is close to useless — long trails (Length near 180) with many accumulated frames saturate to white at the brightest pixels regardless of hue, so both hueShift=0 and hueShift=360 read identically "white." The formula was verified numerically instead (pure arithmetic, no rendering needed) — see the derivation above; that's the part that actually changed.

- All four new fields (`substeps`, `style`, `hueShift`'s new *meaning*, `satShift`) round-trip through `currentPreset()`/scene-load, the transition lerp (`style` snaps at the transition midpoint like other enums; `substeps`/`satShift` lerp numerically, `substeps` rounded), and File Presets export/import — verified end-to-end via a real `?state=` URL generate→reload round trip, not just code inspection.

### Beam glow (`S.beamEdge`, `S.beamCore`, v1.30)

Two independent per-fragment effects sharing the beam shader's existing `d = abs(v_edge)` cross-beam coordinate (0 = centreline, 1 = the beam's true side):
- **Edge** (`S.beamEdge.width/intensity/shape/tintOn/tint/tintAmount`): the pre-existing softness/intensity falloff, now also with a **shape** curve and a **tint**. `t = clamp((d-edgeStart)/(1-edgeStart), 0, 1)` is computed once with well-defined forward arguments, then branched per shape: Soft is the original cubic ease reimplemented as an explicit polynomial (`t*t*(3-2t)`, verified mathematically identical to the old reversed-argument `smoothstep(1.0, 1-width, d)` — same complementary-symmetry identity that lets you flip smoothstep's argument order safely), Linear is `1-t`, Gaussian is `exp(-3t²)`. Tint mixes `col` toward `u_edgeTintCol` in proportion to how faded the pixel already is, so it reads as the edge's own colour rather than a flat wash.
- **Core** (`S.beamCore.width/intensity`): independent of Edge, always evaluated. Whitens `col` toward `vec3(1.0)` within `coreWidth` of the centreline. **Do not write this as `smoothstep(coreWidth, 0.0, d)`** — edge0 > edge1 is undefined per the GLSL spec, and on this project's SwiftShader test target it silently evaluates to 0 everywhere, which is exactly the bug this shipped with initially (looked like the feature did nothing at any setting). Use `1.0 - smoothstep(0.0, coreWidth, d)` instead — correctly-ordered arguments, same resulting curve.
- **Testing gotcha (bit us building this):** an all-white test beam makes "mix toward white" a no-op regardless of whether the code is right or broken — this is the same false-negative class as testing hue-drift on a white beam. Always verify color-shifting effects (core, tint, hue drift, palette-dependent anything) against a saturated, non-white test color, never the default palette.
- Both are gated behind `intensity > 0.001` (and `width > 0.001` for Edge), so `intensity == 0` costs nothing extra and is the default — old scenes render unchanged. `drawBeamGeometry()` zeroes `u_edgeIntensity` and `u_coreIntensity` for its phosphor sub-pass (see "Phosphor walls" above). `edgeTintAmount`/`coreWidth`/`coreIntensity` are `MOD_PARAMS` targets; `shape` (enum) and `tintOn` (bool) are not, matching every other enum/boolean control in the app.

### Beam material: Hue drift (`S.beamHueDrift`, v1.49 rescale)

`beamRgbAt(mat, t)` rotates a beam's hue as `t` (cumulative path distance in px, continuous across every bounce — not reset per-segment, which is the intended "gradient runs through every bounce" behaviour, not a bug) advances: `hh = (mat.h + t * mat.driftPerPx) % 360`. `driftPerPx` used to be `(S.beamHueDrift + perBeamHueDrift[i]) / 1000` — degrees per 1000 **raw canvas px**. Two problems: it scaled with the canvas's actual pixel size (viewport/DPR/window layout — directly relevant after v1.48 let the stage be a bigger rectangle instead of a fixed square), and it was wildly disproportionate to the slider's own ±360 range — a chaotically-bouncing beam easily racks up several thousand px of cumulative path (empirically ~28× the room's own diameter, at a reflectivity around the default, before per-bounce energy loss drops a segment's intensity below the `computePath` cutoff), so even a modest-looking slider value produced several *full* rainbow rotations. Reported as "seems overly sensitive."

Fixed in `buildBeamsOnly()` by normalizing to the room's own scale instead of a flat constant: `roomDiameterPx = min(glCanvas.width, glCanvas.height) / S.dpr` (the exact same quantity `buildShape()` sizes the room from) `; driftPerPx = beamHueDrift / (roomDiameterPx * 50)`. The `×50` tunes overall magnitude — chosen so a *typical* beam's whole path (~28 diameters) lands around half a rotation at the slider's max, versus ~19 full rotations under the old rate. Both properties verified empirically, not just by inspecting the formula: **scale invariance** — the same slider value produces a comparable hue rotation across room diameters spanning 248–984px (a ~4× range) — and **graduated magnitude** — direct pixel-color sampling at hueDrift 0/30/90/200/360 shows a clean progression from pure red (no drift) through a barely-there orange tint (30) to a dramatic red-through-yellow-into-green sweep (360), not "no visible difference until it's suddenly a strobing rainbow."

**Testing gotcha hit verifying this (new, beyond the existing "don't test color effects on an all-white beam" one above):** setting `S.beamPalette` directly in a test does *not* change what actually renders — `buildBeamsOnly()`'s per-beam palette lookup is `S.emitterPalettes[em] || S.beamPalette`, and `S.emitterPalettes` is what the real UI's scheme-change handler (`applySchemeToAllEmitters()`) actually populates; setting `S.beamScheme='custom'` + `S.beamPalette=[...]` alone left the beam rendering whatever `S.emitterPalettes[0]` already held (the grayscale default), reading as pure achromatic grays no matter what hue drift was doing, and very nearly produced a false "the fix doesn't work" conclusion. Fix for tests: also set `S.emitterPalettes = [S.beamPalette]` directly.
- **i18n gotcha (bit us twice — v1.24 `hintTrails`, v1.26 `hintRings`/`geometric`):** every user-facing string lives in FIVE places — the inline HTML default plus all 4 `TRANSLATIONS[lang]` tables. Editing only the HTML default silently regresses the moment a user selects any language (including re-selecting English) — `applyTranslations()` overwrites `textContent` from the table, stale or not. When changing a hint/tooltip/label, update every occurrence, not just the HTML. **`tests/i18n-audit.mjs` now enforces this** (and runs first in CI) — it fails on HTML↔en drift, keys missing from any language, state-toggle buttons carrying `data-i18n`, and dead `TAB_OF_GROUP` entries. Run `node tests/i18n-audit.mjs` after touching any string.
- **Never put `data-i18n` on a button whose caption is state.** `applyTranslations()` sets `textContent` from the table, so a toggle reading "On"/"Off" gets clobbered with its static label on every language change (this is what happened to `#emitterGeoToggle`, which read "Geometric" instead of On/Off after any language switch). State toggles carry no `data-i18n`; their neighbouring `<label>` holds the translatable text. Where a button's caption is *both* state-driven and translatable (`#audioToggle`: "Start listening" ⇄ "Stop listening"), `applyTranslations()` re-asserts the live-state caption after the sweep — extend that tail if you add another such button.

## Scene / preset / localStorage system

- **Scenes (slots 0–7):** stored in `S.scenes[]`, persisted in `localStorage` under `voidulator_state`. Load/save via the Scenes panel or keyboard `1–8`. Smooth transitions interpolate all numeric `S` properties over a configurable duration.
- **Screensaver:** cycles through non-empty slots at a configurable interval (minutes). Activated by the 🌙 button or `N` key advances one slot.
- **JSON export/import:** `savePreset` serializes full `S` to a `.json` file; `loadPreset` merges it back, then triggers a redraw.
- **Factory reset:** replaces `S.scenes` with the 15 hardcoded curated scenes and reseeds 8 screensaver slots.
- **Every optional feature block in `applySceneInstant()`/`applyPreset()` resets to that feature's own defaults when the loaded scene/preset doesn't have it, never leaves the current live value (v1.49 fix).** Reported as: Kaleidoscope on, then choosing a scene saved before Kaleidoscope existed — it stayed on, because the loader did `if (scene.kaleido) { S.kaleido.enabled = scene.kaleido.enabled ?? false; ... }`, and a scene with no `kaleido` key at all skips the *entire* block, not just falls back per-field. Same bug, same shape, independently in both functions, across trails/bloom/kaleido/generative/beamEdge/beamCore/phosphor/rings/widthWave/motion — anything added after some of the user's scenes were already saved. Fixed by dropping the outer guard and using `?.` per field instead (`S.kaleido.enabled = scene.kaleido?.enabled ?? false;`), which was already the working pattern `overlap` used in `applySceneInstant()` — just not applied consistently to the older blocks. **`rings` needed an explicit `else { S.rings.enabled = false; }`** rather than the same per-field treatment, since it's a wholesale `JSON.parse(JSON.stringify(scene.rings))` clone, not built field-by-field — mirrors how `field`'s `else { S.field.enabled = false; }` already handled this correctly (the one block that was never buggy). **Deliberately did NOT touch `modRoutes`/`beat`** in `applyPreset()` — those are rig config loaded separately by `loadModConfig()` before any preset applies, not part of a scene's own data, and `captureScene()` doesn't even serialize them, so they were out of scope for this bug. When adding a new optional `S.X` sub-object to a scene's shape, use `scene.X?.field ?? default` for every field, never `if (scene.X) { ... }` — the guard is exactly the bug.

### Viewer links (v1.46)

A per-scene "watch, don't touch" URL: `?scene=<base64 captureScene()-shaped JSON>&view=1`, distinct from the existing `?state=<base64 currentPreset()-shaped JSON>` share link and deliberately not merged with it — the two links carry different object *shapes* (scene tiles already store `captureScene()`'s shape in `S.scenes[i].data`; reusing it directly avoids a shape conversion, but means the loader has to know which restore function pairs with which param).

- **Generation**: each `.scene-thumb` tile gets a small 🔗 icon (`.scene-thumb-link`, styled like `.group-reset` — subtle by default rather than invisible-until-hover, since a dense 4-column grid needs the affordance to be scannable). `generateViewerUrl(sceneData)` + `copyViewerLink(scene, btnEl)` mirror `generateShareUrl()`/`copyShareUrl()`'s clipboard-write-with-`execCommand`-fallback pattern, except the fallback is a `window.prompt()` (no dedicated `<input>` to `select()` the way the share modal has one).
- **Loading**: `loadViewerFromUrl()` sits *before* `loadFromUrl()` in `init()`'s load-priority chain (viewer link → share link → autosave → startup preset) and sets module-level `viewerMode = true` on success. Unlike `loadFromUrl()`, it does **not** clear the URL after loading — a viewer link is meant to be a stable, reloadable/bookmarkable pointer at one scene, not a one-shot transfer.
- **Landing state, and why it's a two-step flow (v1.46 first shipped this as one auto-applied step; reworked same day after real-world testing)**: the *first* version set `isFullscreen = true` directly on load, skipping `requestFullscreen()` because the native API throws without a user gesture and a page load never has one. That broke the F key: since `toggleFullscreen()` just does `isFullscreen = !isFullscreen`, and it was already `true`, the *first* press of F flipped it to `false` and revealed the panel — the opposite of what F is supposed to do, and exactly the bug reported. **Real fullscreen turns out not to be skippable** — it has to be requested from an actual click, so there has to be a click to request it from. `init()` now only adds the CSS (`fullscreen-mode hide-ui viewer-mode` on `body`, hiding `.panel` immediately) and leaves `isFullscreen`/`uiHidden` at their real default (`false`) until the splash's own **Fullscreen button** is clicked, which calls `window.enterViewerFullscreen()`: that requests native fullscreen (a genuine gesture now), and *only on success/failure/no-API-at-all — always, via `.then(proceed).catch(proceed)`, so a denial or an unsupported browser can't strand the viewer* — sets the real `isFullscreen`/`uiHidden` state and adds `body.viewer-ready`, which swaps the splash's Fullscreen button for a **Watch button** (CSS keyed off `.viewer-ready`). Watch calls `dismissSplash()`, finally revealing the (already-hidden-panel) canvas.
- **`dismissSplash()` gates on `viewer-mode`+`viewer-ready`, not just where it's called from.** The overlay's `onclick="dismissSplash()"` (click-anywhere) and the unconditional `setTimeout(window.dismissSplash, 8000)` auto-dismiss are both still wired up exactly as before, unconditionally — putting the guard *inside* the function (return early if `viewer-mode` is set but `viewer-ready` isn't) was simpler and more robust than trying to conditionally detach those two separate call sites, and correctly still lets the Watch button's call through once `viewer-ready` is there. `body.viewer-mode` is set early in `init()`, well before either of those paths could possibly fire, so there's no ordering race despite the splash's own setup code running at top level before `init()` is even called.
- **Not a lockout**: because the real `isFullscreen`/`uiHidden` state only gets set once fullscreen is actually confirmed (not assumed on load), the ordinary F/U toggle logic behaves exactly as it does outside viewer mode from that point on — a curious viewer can still get back to the full editor. This is also true *before* the Watch button: pressing F while the splash is still up goes through the same real flow (a keypress is a valid gesture too) and correctly enters fullscreen without ever revealing the panel, since `hide-ui` was already forced on and `toggleFullscreen()` only clears it when going *from* `true`.

## Undo/Redo (v1.44)

Fusion-style step back/forward: `#btnUndo`/`#btnRedo` in `.header-buttons`, plus Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y (all gated behind `isTypingInInput()`, same guard the other global shortcuts use). In-memory only, one linear array (`undoHistory`, JSON strings) + `undoCursor` — not persisted across reloads, session-scoped like most creative-tool undo stacks.

- **Reuses the existing scene capture/restore pair** (`captureScene()`/`applySceneInstant()`, the same one scene slots and transitions already use) rather than inventing a second serializer. Snapshots are stored as **JSON strings, not live objects** — `captureScene()` returns several fields by direct reference (`beamPalette`, `emittersNorm`, …), so storing its return value as-is would let a later in-place edit silently mutate an already-recorded history entry.
- **Commit trigger**: piggybacks on the *existing* delegated `['input','change','click']` listener (near `requestAutosave()`) that already fires for every control in `.panel` — added a second debounced call (`requestUndoSnapshot()`, 500ms, separate timer from autosave's 2s) right alongside it, rather than wiring up undo tracking in each of the ~150 individual `_on(...)` handlers across the file. This means any future control that participates in the existing autosave convention (i.e., lives in `.panel` and fires `input`/`change`/`click`) is automatically undo-tracked with zero extra code — don't bypass this listener for a new control's own event flow, or it silently won't be undoable.
- **`stripVolatile()` — the non-obvious part.** `captureScene()` includes fields that are continuously-advancing animation phase, not user-authored settings: `perBeamPhase` drifts every frame the instant any beam has a nonzero per-beam speed (true by default via the Per-Beam Rotation pattern — **this bit us**: an early version compared raw `captureScene()` JSON for the "did anything actually change" dedup check, which is *never* true two frames apart with default settings, so it looked fine on individual clicks but silently discarded the redo branch a fraction of a second after every undo/redo). Also drifts: `angleDeg` (Global speed), `trails.driftPX/PY/Heading/Phase/ShapeRot` (Drift motion), `rings.rot`, `field.rot`/`phase`/`pulsePhase`. `stripVolatile()` deep-clones a snapshot and deletes these before the equality check *only* — the **stored** snapshot keeps the real values, so restoring one is still faithful (undo does briefly snap the angle/phase back, which is expected and fine), only the "should I record a new step" decision ignores them.
- **Don't let clicking Undo/Redo re-arm their own commit timer.** The delegated listener above fires in the CAPTURE phase on `document`, so it sees a click on `#btnUndo` *before* `restoreUndoState()`'s own `undoRestoring` guard is ever set — the guard doesn't help here since the timer it would need to suppress fires 500ms *later*, well after the guard has already reverted to `false`. Fixed by explicitly excluding `#btnUndo`/`#btnRedo` from the `requestUndoSnapshot()` call (autosave still fires for them, harmlessly, and `restoreUndoState()` calls it again anyway). `stripVolatile()` alone would likely have masked this too, but excluding history-navigation clicks from being treated as edits is the more correct fix regardless — semantically, Undo isn't an edit.
- **`restoreUndoState()` calls `rebuildSegStrip()`/`syncSegmentsUI()` explicitly** — `applySceneInstant()`'s own tail already handles most rebuild/sync (`rebuildBeamSwatches`, `rebuildBeamSpeedInputs`, `syncUIFromState` → `rebuildPerBeamEditor`), but not the segment editor strip, which only rebuilds from its own edit handlers today. Verified beam-count-changing edits (add/remove a beam) round-trip correctly through undo, including the per-beam chip UI.
- **Testing gotcha (same class as the CSS-transition one two sections up):** none here — this system is pure synchronous JS with no CSS animation, so unlike the collapsible-group fix, short waits in automated tests are reliable. The gotcha that *did* bite here was purely the volatile-field one above, not timing.

## Stage aspect ratio (v1.48, v1.50)

`.stage` (and therefore the GL canvas — `resize()` reads `glCanvas.parentElement.getBoundingClientRect()` and sets `glCanvas.width/height` to match exactly, no square assumption anywhere in that path) is **not** locked to a square on desktop. It never needed to be: `buildShape()` already computes the room shape from `safeR = Math.min(W, H) / 2 - margin` and centers on `(W/2, H/2)` — a circle/polygon room is correctly inscribed in the *smaller* of the two dimensions regardless of the canvas's actual aspect ratio, so a wider-than-tall canvas just leaves genuine extra rendered space on the sides, not a distorted room. The only thing that was ever forcing square was two CSS properties on `.stage` (`aspect-ratio: 1/1` and `max-width: calc(100vh - 16px)`) with no JS-side dependency on them at all — removed, so `.stage` now fills the full rectangular area of its grid column.

**Why bother**: Trails' Zoom/Spin feedback already smears content past the room's own boundary once Walls is off (see Trail ping-pong above) — that's old, working, intentional behavior. On a square canvas that smear had nowhere to go once it reached the canvas edge a few hundred px in from the panel, on any reasonably wide monitor, with the leftover rectangular space simply unused (visible as black `.app` background beside the square). Now that space is real canvas. Verified empirically, not just by inspecting the CSS: with Zoom+Spin+Trails running and Walls off, sampled pixel regions well outside the circle's radius near the canvas's own left/right edges came back **100% lit** — content that had no canvas to exist on before this change.

- **Mobile (`@media max-width: 800px`) keeps its own separate, self-contained `aspect-ratio: 1/1` rule**, for an unrelated reason (a tall phone viewport with the stage stacked above a scrolling panel benefits from a fixed, predictable shape — see that rule's own comment) — untouched, and unaffected by the base rule's properties changing since it re-declares its own `width`/`height`/`aspect-ratio` rather than inheriting them.
- **Fullscreen/hide-ui viewer mode kept its own square through v1.49** (`body.fullscreen-mode.hide-ui .stage { width: min(100svw,100svh) !important; ... }`, see the Undo/Redo-adjacent Viewer links section) — a more specific rule with `!important`, entirely independent of the base rule, so v1.48's fix never reached it. v1.50 applied the same fix there (`100svw`/`100svh`, dropping the `min()`): worth fixing specifically *because* it's the mode viewer links land in and F+U reaches manually — the one place someone opens specifically to just watch, and therefore the one place Trails' Zoom/Spin roam mattered most. Verified with the same pixel-sampling technique as the base rule: `.stage`'s measured box now matches the full viewport rectangle (not `min(w,h)`), and with Trails/Zoom/Spin running in that mode, lit pixels reached past the old square's half-extent on the long axis.
- **Verified room-shape math is untouched** (a circle's measured `R` still equals `min(canvasW,canvasH)/2 - margin` exactly) and that Rings/Wave field/Generative all still render correctly with zero GL errors on a genuinely rectangular canvas. **Kaleidoscope did not get the same clean bill of health** — see the next section. Zero GL errors turned out not to mean zero visual bugs; a shape can render "successfully" and still be the wrong shape, and that gap wasn't caught until pixel-level verification in v1.50, one version later than it should have been.

## Kaleidoscope aspect correction (v1.50)

`kfold()` (the shared GLSL folded into both `copyFs` and `blitFs` via the `kscopeGlsl` template literal) reconstructs the mirrored-wedge pattern by converting each pixel to a radius + angle around the center, folding the angle into a `2π/segments` wedge, and converting back. It did that conversion directly on normalized `[0,1]` UV coordinates — geometrically square only when the canvas itself is, which was always true before v1.48. Once the canvas could be rectangular, one UV unit on the long axis started covering more real pixels than one UV unit on the short axis, so `length()`/`atan()` computed on raw `uv - 0.5` measured a stretched notion of radius/angle: the fold came out squished into an ellipse along whichever axis was longer. This shipped unnoticed in v1.48 because that thread's own verification only checked for GL errors on a rectangular canvas, not visual correctness — an easy gap to miss since the shader compiles and runs fine either way, it just draws the wrong shape.

- **Fix**: new `u_kRes` uniform (canvas resolution, uploaded in `uploadKscopeUniforms()` — the single centralized per-program-bind uniform upload point, so one new line covers every call site) multiplies `uv - 0.5` before the polar math and divides the reconstructed point by it after. On a square canvas `u_kRes.x == u_kRes.y` and the two scalings cancel out exactly — algebraically a no-op, not just "probably fine."
- **`u_kRes` is uploaded as raw `glCanvas.width/height`** (DPR-inclusive), unlike the main beam shader's `u_res` which divides by `S.dpr` — an intentional inconsistency, harmless here since only the *ratio* between the two axes matters for aspect correction and DPR scales both equally, but worth knowing if this uniform is ever reused for something that needs absolute pixel units.
- **Verified** by rendering the same kaleidoscope scene (fixed beams, no rotation, segments=6) at a square canvas, a wide canvas (aspect 1.58), and a tall canvas (aspect 0.25), then measuring the lit pattern's own bounding-box aspect ratio each time: 0.995, 0.993, 0.995 respectively — a round/regular core regardless of canvas shape, where the old math would have tracked the canvas's own aspect ratio instead. The square case matching pre-fix behavior (via the algebraic no-op) confirms no regression for anyone not using the rectangular stage.

## Panel tools (tabs / search / reset / thumbnails)

`initPanelTools()` (called early in `init()`, before `loadLanguage()`) tags every `.group` with `data-group-key` (its title's `data-i18n` key) and `data-tab` (from `TAB_OF_GROUP`), builds the search+collapse toolbar and the tab bar, and attaches per-group ↺ reset buttons. Resets restore from `FACTORY` — a deep snapshot of S taken by `snapshotFactory()` at the **top of init(), before autosave/URL loading** — via the `GROUP_RESETS` map (add an entry there when adding a new group). The reset span is a **sibling** of the title, not a child: `applyTranslations()` rewrites title textContent and would destroy children. Tab/search visibility uses `.tab-hidden`/`.search-hidden` classes (`display:none !important`), never inline styles, so it composes with the simple/advanced mode CSS. Scene thumbnails (`captureSceneThumb()`, 96×72 JPEG dataURL) are stored on the scene objects at save; scenes visited without one get captured ~0.5 s after their transition settles (`pendingThumbScene` in `loopBody`).

**Sticky top (v1.43, reworked v1.45):** `.panel-header` (title/icons) and `.panel-tabs` are each independently `position: sticky; top: 0` (not wrapped in a shared container). `.panel-tools` (the search input + collapse/expand-all buttons), built and inserted between them by `initPanelTools()`, stays in normal flow and scrolls away — deliberately: it's not needed once you're mid-scroll scanning a group's content the way the nav is. `.panel` is the scrolling ancestor (`overflow: auto`), so header/tabs stay pinned while a long group list scrolls underneath (Scenes, mainly, but any tall group).

- **v1.43 shipped a single `.panel-sticky-top` wrapper around all three** (header+tools+tabs). Two bugs came from that: (1) the user could see a sliver of scrolled-past content above the wrapper at certain scroll positions — root cause never fully pinned down remotely (no working screenshot tool in that session), but the fix that provably eliminates it regardless of the exact mechanism is giving `.panel-header` (now the *first* sticky element with nothing above it) a **negative top margin equal to `.panel`'s own top padding** (`margin: -14px -14px 12px`), so its opaque background reaches `.panel`'s true top edge with zero seam for anything to show through — verified by scripting `.panel.scrollTop` through the *entire* scrollable range in 30px steps and confirming nothing ever renders above `.panel-header`'s top at any of them, not just one or two spot-checked positions; (2) the user wanted the search bar excluded from the pinned group, which needed splitting the one wrapper into two independent sticky elements anyway.
- **Two sibling `position: sticky; top: 0` elements do NOT auto-stack — this bit us mid-fix.** The natural assumption ("second one starts sticking once the first is out of its way") is wrong; both try to stick at the same `top: 0` and overlap, whichever has higher `z-index` (header, 20 vs tabs, 19) visually winning. `.panel-tabs` needs `top` set to `.panel-header`'s actual rendered height so it starts sticking exactly where header ends. That offset is **not hardcoded** — a `ResizeObserver` on `.panel-header` (same pattern the stage canvas already uses for its own resize handling, see `init()`) keeps `tabBar.style.top` in sync automatically, so a header height change from any cause (language switch wrapping the title to two lines, a font load, a future extra button) can't silently reintroduce the overlap the way a fixed pixel guess would. Verified: `.panel-tabs`'s top edge sits exactly at `.panel-header`'s bottom edge (0px gap, 0px overlap) once both are scrolled into their stuck position.
- `.panel-tabs` itself only needs `margin: 0 -14px` (sides) to reach `.panel`'s edges — no top-margin cancellation, since it's not the topmost element anymore; that's `.panel-header`'s job alone.

## Panel layout: labels wrap, never clip

`.grid` (125px) and `.subgrid` (105px) have **fixed** label columns, so `label` uses `white-space: normal` + `overflow-wrap: break-word` — long labels wrap to a second line instead of running underneath their own control. Do not reintroduce `white-space: nowrap`: English labels are the *short* case, and translations are far longer (French "Sur le temps : saut de teinte" needs 223px), which is how 26 French labels ended up clipped through v1.26. Prefer short label text where a group's context already supplies the meaning — inside TRAILS, "Zoom/Spin/Drift X/Drift Y" beats "Feedback zoom/…". To re-check, measure `scrollWidth - clientWidth` over `.panel label` in all four languages; it must be 0.

## UI conventions

- **Simple / Advanced mode:** `body.mode-simple` hides all `[data-advanced]` and `.advanced-only` elements. Toggle is in ⚙️ Settings.
- **i18n:** elements with `data-i18n="key"` are updated by `applyI18n()` when language changes. Four languages: `en`, `es`, `pt`, `fr`. Strings live in the `I18N` object in the JS section.
- **Collapsible groups:** `.group.collapsible` sections toggle with `.collapsed` class; state is not persisted. The expand/collapse animation is a `max-height` transition (can't transition to/from `none`, so it needs a real pixel value on each edge). **Do not go back to a hardcoded ceiling on `.group-content`** (the pre-v1.43 code used `max-height: 500px` as a "comfortably larger than any group" guess) — `overflow: hidden` then silently clips anything past it with no scrollbar to reach the rest, which is exactly what happened to Scenes once a user had saved enough of them (a 4-column thumbnail grid clears 500px well under 20 scenes). `setGroupCollapsed(g, collapsed)` (near the per-title click handler) measures instead: on expand it reads `content.scrollHeight` and animates up to that, then on `transitionend` releases the cap to `max-height: none` entirely — so it's a real constraint only *during* the animation, never at rest, and can't be invalidated by content that grows later while the group is already open (adding another scene, another segment, another beam's trim chip). On collapse it first pins `style.maxHeight` to the current `scrollHeight` (so there's a real "from" value — max-height can't animate from `none`), then sets it to `0` on the next frame via a double `requestAnimationFrame` (forces the browser to commit/paint the pinned value before changing it again, otherwise the two writes can coalesce into one and the transition never visibly runs). All three toggle sites (per-title click, Collapse-all, Expand-all) go through this one function now — don't reintroduce a raw `classList.toggle('collapsed')`/`add`/`remove` anywhere, it'll skip the measurement and silently reintroduce the clipping bug. **Testing gotcha hit verifying this:** under headless SwiftShader with the app's own per-frame WebGL loop running, a 250ms CSS transition can take several real seconds to visibly settle (same class of unreliable timing as the frame-benchmarking caveat above) — a naive test with a few-hundred-ms wait reads a stalled mid-transition state and looks like a regression that isn't one; wait multiple seconds (or check the *final* settled value, not one read shortly after the toggle) before trusting a collapse/expand test result.
- **Clickable labels (v1.33): click a label, its control resets to factory default.** Two parallel mechanisms share the same `label.clickable` CSS: (1) four original hand-written handlers (Beam Shapes' Density/Size/Flow/Spin — `lblDensity`/`lblSize`/`lblFlow`/`lblSpin`, each a one-off `_on(el,'click',...)` setting `S.x` + the input's `.value` directly); (2) `RESET_DEFAULTS` + `initClickableResets()` (near `GROUP_RESETS`), a generic data-driven version covering ~60 sliders app-wide. For the generic path, the label carries `data-reset="<inputId>"`; one delegated click listener on `.panel` looks up `RESET_DEFAULTS[id]()` (the value to put IN the slider — usually straight from `FACTORY`, occasionally a literal for the handful of fields FACTORY's snapshot never picked up, same gap `GROUP_RESETS.bonus`/`roomTitle` already have), sets `input.value`, then **dispatches a real `input` event** rather than touching `S` directly — this replays whatever handler a manual drag would've fired, so every side effect (paired number-input sync, `rebuildSegStrip()`, `applyEmitterCluster()`, autosave, etc.) stays correct with zero duplicated logic. Adding a new resettable slider: add its label's `class="clickable" data-reset="theInputId"` and one `RESET_DEFAULTS` entry — nothing else. Excluded on purpose (no single global default exists): per-beam trim sliders (`pbOpacity`/`pbAbsorb`/`pbHueDrift` — already have their own `perBeamReset` button for the selected beam) and per-segment-item sliders (`segWidth`/`segOpacity`/`segSoft`/`segItemWavelength`/`segItemSpeed` — selected-item-dependent). **Don't read defaults from a handler's `parseFloat(...) || N` fallback or from the HTML `value=` attribute — both have drifted from the real `FACTORY` default before** (`fieldGain` handler fell back to 1.4 against a real default of 2.5; `audioSensitivity` fell back to 1.5 against a real 4); `FACTORY` (or, if genuinely absent from it, the true `S` init literal, verified by reading the object, not guessed) is the only trustworthy source. `speedMultiplier` is the one control where slider-space ≠ stored-value-space (`sliderToSpeed`/`speedToSlider`, a log curve) — its map entry must return `speedToSlider(FACTORY.speedMultiplier)`, not the raw stored value, or the dispatched input event double-transforms it.

## Rings system

`S.rings` (own panel) is an independent emission layer that coexists with beams — `renderBeamsGL` calls `buildRingGeometry()` whenever `rings.enabled`, before/alongside the beam loop (`S.beamCount` may be 0 for rings only). Key pieces:

- **Own emitters**: `S.rings.emittersNorm` (norm coords like beam emitters, teal dots in the overlay, draggable via `S.ringDraggingIdx`). `arrangeRingEmittersGeometric(anchor)` places N emitters as a regular polygon around the room center through the anchor dot (the most recently dragged one, `ringLastMoved`).
- **Folded-wavefront renderer**: `RING_RAYS` (240) rays per emitter traced once via `computePath` and cached (`ringRays`, keyed on geometry + ring-emitter positions + bounce cap). The ring at expansion distance `d` is the point at distance `d` along each folded ray. Fold detection skips connections > ~4× the expected arc gap.
- **Lifetime in legs**: per-ray death at `lifetime × ray.firstLeg` (1 = birth→wall, 2 = back at center…), then alpha fades over `rings.fade` seconds. Bounce cap for tracing = `ceil(lifetime/2)+4`, max 64.
- **Spawning**: `advanceRings` runs a randomized scheduler — activation every `randIn(interval)` s, each activation queues `randIn(perActivation)` rings spaced `randIn(spacing)` s apart (`pendingRings` countdowns). `activateRings()` is also the manual button / debug API. Rings are ALWAYS born at d=0 (at the emitter).
- **Dual-range sliders**: `makeDualRange(slotId, …)` builds the two-thumb min/max control; `randIn(range)` draws the value. Reuse this for any future [min,max] randomized parameter.
- Ring width floors at ~1.2px (sub-pixel quads alias into moiré). Taper uses per-ray life progress.

## Emitters & formation clusters

All three emission systems (beams, rings, wave field) keep their emitters as `{nx,ny}` norm coords and share one set of formation helpers (defined once, used by all):
- `normToRoomPx(arr)` / `writeNormFromPx(arr,i,px)` — convert between norm and room-px via `getRoomBounds()`.
- `roomCenter()` — circle centre or polygon **centroid** (the visual middle; for a triangle this is NOT the bbox centre — that distinction caused the wave-field off-centre bug, fixed by centring the field square on the centroid).
- `defaultFormationRadius()` — 0.28×min room dim; used so a collapsed (all-at-centre) formation spreads instead of stacking.
- `arrangeFormationGeometric(arr, anchorIdx)` — lay out as a regular polygon (2=line, 3=triangle, 4=square…) anchored on one dot; `centerFormation`, `uprightFormation`, `setFormationCount`, and `rotateFormationBy(arr, deltaDeg)` (rotate around centre, preserving radius — drives manual Rotation + auto Spin).

Per-system specifics:
- **Beams** (`S.emitters` / `S.emittersNorm`): cluster params `emitterGeo` (align/drag-follow on), `emitterRot` (deg), `emitterSpin` (deg/s), `emitterRadiusN`. `applyEmitterCluster()` lays them out; `moveEmitterSymmetric(idx,pos)` derives radius+rotation from a drag and re-applies so the rest follow. `setEmitterCount` / `randomizeEmitters` call the cluster when `emitterGeo`.
- **Rings** (`S.rings.emittersNorm`, teal dots) and **field** (`S.field.emittersNorm`, magenta dots): each has `geometric`, `rot`, `spin`; manual rotation applies the delta via `rotateFormationBy`, spin advances in `loopBody`. Field spin just relocates wave sources (cheap). **Ring spin used to re-trace the whole ray cache every frame** (emitters moved → `ensureRingRays` rebuilt), costing 3–9 ms/frame with 2+ ring emitters. Since v1.36 that is avoided in **circle rooms only**, via the rotation-equivariance argument below.

### Ring spin fast path (circle rooms, v1.36) — and the invariant it rests on

`ensureRingRays()` has two modes, tagged in `ringRaysKey.mode`:
- `'circleRot'` — a circle is rotationally symmetric about its centre, and `rotateFormationBy()` explicitly re-places each emitter at its *own preserved radius*, so spinning moves every emitter along a circle concentric with the room. The path traced from a rotated emitter is therefore **exactly** the path from the unrotated one, rotated by the same angle. So the cache is keyed on each emitter's **radius** (quarter-pixel buckets, matching the pre-existing position tolerance), rays are traced once from a canonical point at angle 0, and `ringRayRot[em]` (`cos`/`sin` about the room centre, plus `hueSteps`) rotates the points at draw time in `buildRingGeometry`. Pure spin never invalidates the cache.
- `'poly'` — everything else keeps the original behaviour (key on emitter positions, re-trace when they move), because non-circular rooms are **not** rotation-invariant.

Things that will silently break this if changed:
- **`rotateFormationBy` must keep preserving each emitter's radius.** If it ever moved emitters off their own concentric circle, the cached-and-rotated path would stop matching a fresh trace.
- **`roomCenter()` must stay the circle's own centre** for circles — it is the symmetry axis the whole argument depends on.
- **The rotation must be applied as an absolute angle** derived from the emitter's current position (`atan2`), never accumulated frame to frame, or float error would drift.
- **Both** places that read a cached point need the rotation: the drawn ring position *and* the phosphor wall-strike point. Rotating the interpolated point (rather than each endpoint) is deliberate and safe — rotation is affine, so it commutes with the lerp.
- **Rainbow hue** is keyed to a ray's *absolute* emission direction. Canonical ray `k` leaves at `a_k`; rotated by `ang` its real direction is `a_k + ang`, so the hue table is read `hueSteps` along to keep the colour pattern fixed in room space. Rounding to whole ray-steps adds no error the sampling didn't already have — the rays themselves are one step apart.

**This is an identity, not an approximation** — the distinction that matters, because approximating ring/beam geometry is exactly what caused the v1.29 jitter. It was verified that way too: frame-to-frame brightness discontinuity over 200 spinning frames is statistically identical to the old code (same count of >5% jumps, zero >15% jumps in both), and all room-shape × spin × emitter-count combinations still render. Note the output is *not* bit-identical to a fresh trace — tracing from `(cx+r, cy)` and rotating differs from tracing at the original coordinates by ~1e-13, which billiard dynamics amplify over 8–16 bounces. That is a different arrangement of the same chaotic system, not instability; the jitter measurement is what establishes it is not a regression, so **re-run that measurement rather than a pixel diff if you touch this.**
- Drag routing in the overlay pointer handlers: `S.draggingIdx` (beam), `S.ringDraggingIdx`, `S.fieldDraggingIdx`. Cluster params persist via scene/preset (beams explicitly; rings/field via whole-object JSON clone, defaulted in the apply migrations).

## Phosphor walls

512 perimeter energy bins (`phosR/G/B`); beam bounce points deposit color via an angle→bin LUT (`phosLUT`, built in `ensurePhosphorGeometry` whenever the wall geometry changes — keyed on the `S.vertices` array reference). Bins decay exponentially in `updatePhosphor`. `appendPhosphorQuads()` writes inward-fading quads into `vertBuf` **after** the beam geometry; `drawBeamGeometry()` draws beams first, then the phosphor range with `u_segOn`/`u_edgeIntensity`/`u_coreIntensity` zeroed so the wall glow doesn't pulse, band, or show a hot-core streak. Because phosphor lives in the same draw call, it inherits trails, bloom, and blend modes with no pipeline changes.

## What to watch out for

- The `S` object snapshot in `saveScene()` must deep-clone arrays (emitter positions, beam colors) — shallow copy causes all scenes to share references.
- `requestAnimationFrame` IDs are tracked in `rafId`; always cancel before re-requesting to avoid duplicate loops.
- Audio context must be created on a user gesture; `audioToggle` handles this gate. Same for `requestMIDIAccess` (the Enable MIDI button).
- The `spread` value (beam fan angle) is in degrees in `S` but converted to radians before the ray-trace loop.
- Beam shader uniforms are uploaded in exactly ONE place: `uploadBeamUniforms()`. It used to be three copy-pasted blocks, and a partial refactor of one copy black-screened the live site. Never duplicate it again. `drawBeamGeometry()` re-sets `u_segOn=0`/`u_edgeIntensity=0`/`u_coreIntensity=0` for the phosphor pass so wall glow ignores those.
- **`.stage` fullscreen CSS: `aspect-ratio` needs one dimension left `auto` (v1.31 fix).** `position:fixed; inset:0` pins all four edges, making width AND height definite — `aspect-ratio:1/1` then has nothing to compute and is silently ignored, stretching the room out of square (this is what broke Android fullscreen). The fix sizes the square directly instead — `width`/`height: min(100svw, 100svh)`, centred via `top/left:50% + translate(-50%,-50%)` — rather than relying on `aspect-ratio` to rescue an already-pinned box. Three separate `.stage` rules all apply in fullscreen (unconditional desktop, the `max-width:800px` mobile override, and `.hide-ui`) plus the native `:fullscreen`/`:-webkit-full-screen` pseudo-classes fire independently of the app's `.fullscreen-mode` class — any floor/ceiling (`min-height`, `max-height`, `max-width: calc(100vh - 16px)` from the base rule) left un-overridden in ANY of these will silently win via the normal box-sizing algorithm (floors/ceilings apply after `width`/`height` resolve, regardless of `!important` on the value they're capping) and re-break squareness on whichever screen shape happens to hit that rule. If you touch fullscreen sizing again, override `min-height`/`max-height`/`max-width` with `!important` in all three `.stage` rules, not just the one you're editing, and test a short/wide window in addition to phone portrait/landscape.

## Blend modes (v1.26)

`setBlendMode(mode)` is the ONE place `gl.blendFunc`/`gl.blendEquation` get set for beam-adjacent drawing (mirrors the `uploadBeamUniforms()` single-source-of-truth rule above — don't duplicate it). Five modes, all just GL state (no shader changes):
- **normal**: `FUNC_ADD`, `(SRC_ALPHA, ONE_MINUS_SRC_ALPHA)`.
- **additive**: `FUNC_ADD`, `(SRC_ALPHA, ONE)`.
- **screen**: `FUNC_ADD`, `(ONE_MINUS_DST_COLOR, ONE)` — computes `src + dst − src·dst`.
- **lighten**: `gl.blendEquation(gl.MAX)` — per spec, MIN/MAX **ignore** the blendFunc factors entirely, so the `blendFunc(ONE,ONE)` call alongside it is cosmetic only.
- **difference**: `gl.blendEquation(gl.FUNC_REVERSE_SUBTRACT)`, `(ONE, ONE)` → `dst − src`, clamped ≥0. GL has no true `|a−b|` blend op, so this is a one-directional approximation, not literal Photoshop Difference.

**Difference is genuinely self-extinguishing — this is expected, not a bug.** It can only ever *subtract* brightness, never add it, so: (a) on a fresh scene with no trails it renders solid black forever (every frame clears to black, then `dst−src` on a black dst is always ≤0); (b) even switched on mid-session against bright built-up trails, it erodes back to black within a handful of frames (measured: an avg-brightness-82 scene dropped to 0 in ~6 frames) and then stays there, since there's no mechanism to ever push it back above 0 once every source drawn while it's active goes through the same subtractive blend. It's a brief live flourish (flip to it momentarily to carve into existing glow), never a steady look — don't try to make it one without adding a genuinely different mechanism (e.g. periodically drawing something in a different mode to replenish brightness).

**Any pass that must stay additive regardless of `S.blendMode` must explicitly reset BOTH `blendEquation` and `blendFunc`, not just one.** `compositeWithBloom`'s glow layer is exactly this case (see above) — it was originally written back when every mode used `FUNC_ADD`, so only resetting `blendFunc` was safe; that assumption broke the moment Lighten/Difference introduced other equations. If you add a mode with yet another `blendEquation`, audit every raw `gl.blendFunc(...)` call that isn't inside `setBlendMode` for the same gap (currently there is exactly one: the bloom glow blit).

## Beam material (per-beam) + Wave-field colour (v1.20–1.21)

- **Beam material is baked on the CPU, not the shader** (v1.21 reworked v1.20's shader-uniform approach). `pushQuad` computes per-*vertex* colour + alpha from a per-beam `mat = {h,s,l, baseRgb, opacity, absorbK, driftPerPx}` via `beamRgbAt(mat,t)`/`beamAlphaAt(mat,alpha,t)`: opacity is a constant alpha multiply, absorption is `exp(-t·absorbK)` (t = the vertex's cumulative path px), hue drift rotates the HSL hue by `t·driftPerPx` and re-runs `hslToRgb`. This keeps the **vertex layout at 8 floats** (shared with rings + phosphor + `appendPhosphorQuads` — do NOT expand it; that's the black-screen hazard) and makes every property **per-beam** with no shader change. The GPU interpolates linearly within a segment; hue rotation across a *very* long single bounce-leg cuts a slight RGB chord (subdivide later if it matters).
- **Master × per-beam trim model.** Globals `S.beamAlpha/beamAbsorb/beamHueDrift` (Modulation targets, "Beam Material" group master sliders) combine with per-beam arrays `S.perBeamOpacity[]`(×,def 1) `S.perBeamAbsorb[]`(×,def 1) `S.perBeamHueDrift[]`(+,def 0): effective opacity=master×trim, absorb=clamp(master×trim,0,2), hueDrift=master+trim. Arrays sized by `ensurePerBeamMaterial(n)` (mirrors `ensureSpeedArrays`), rebuilt in the editor by `rebuildPerBeamEditor()` (chip strip + selected-beam trim sliders; `selectedBeam` is UI-only). Persisted in scene+preset, element-wise lerped in transitions, reset via `GROUP_RESETS.beamMaterial`.
- **Wave-field Prism + Fog** (`S.field.colorMode==='prism'`, `S.field.fog`): Prism (mode 3) computes each RGB channel from the displacement at a 120°-offset cosine phase → soft chromatic gradients (the generic per-channel-phase-offset technique, à la Silexars' "Creation"; independently written, RESEARCH.md §22). Fog lifts calm (low-|displacement|) regions with a slow cosine-drifting haze tint instead of black. Both driven by a `u_ptime` (seconds) uniform on `waveColorProg`; `fieldFog` is a `MOD_PARAMS` target.
- The render loop is `loop()` (try/catch + rAF rescheduling + error badge) wrapping `loopBody()` (the actual frame). A throwing frame must never stop the loop — keep that structure. `Voidulator.step(t)` drives `loopBody` directly for tests (rAF doesn't fire in hidden tabs).
- `applyModulation()` must run **before** the rotation/phase integration in `loopBody()` (so a modulated `rotationSpeed` actually spins faster) and `restoreModulation()` **after** `drawOverlay()`/`captureRecFrame()`. Don't reorder.
- **Segments (v1.23, replaced Pulse).** The beam fragment shader composites up to `MAXSEG` (8) soft-edged segment bands over the solid beam. Non-drift segments tile one global cycle — phase `fract(v_t·u_invSegWl − u_segScroll − start_i)`, active when `< width_i`; drift segments (`u_segDrift[i]`) scroll on their own `fract(v_t·u_segInvWl[i] − u_segTime·u_segRate[i] − start_i)`. Coverage is a periodic soft band around each segment's centre (softness×width); higher-index segments `mix()` over lower, gaps fall back to the beam colour; `u_segCount<1.5` ⇒ solid (a single segment is never a cycle). Two runtime-only clocks in `loopBody`: `S.segScroll` (global cycle offset, integrated from `speed/wavelength`, wrapped to [0,1) — continuous under modulation, don't replace with raw `time×speed`) and `S.segTime` (bounded seconds, for drift). Segment arrays are built + uploaded once in `uploadBeamUniforms()` via reused `_seg*` `Float32Array` scratch + `segLayout()` (normalised widths/starts). `readSegments()` reads the new shape or migrates old pulse fields; `lerpSegments()` interpolates (per-field when counts match, snap at t=0.5 otherwise). UI: `rebuildSegStrip()`/`syncSegmentsUI()`, `selectedSeg` is UI-only.
- `buildShape()` floors the room radius at 10px (`safeR`) — a hidden/collapsed stage reports near-zero size and a negative radius makes canvas `arc()` throw. `resize()` floors the canvas backing store at 2px for the same reason.
- The canvas is sized by `resize()`, called on `window.resize` **and** a `ResizeObserver` on the stage. The observer is essential: it recovers the canvas if the first `resize()` ran before layout settled (otherwise it sticks at the 2px floor → blank stage), and it catches reflow / mobile address-bar changes that don't fire a window resize.
- Wall bending: `buildShape()` caches unbent corners in `S.baseVertices`; `bendWalls()` re-derives both `S.vertices` (drawing/point-in-room polyline) and `S.wallArcs` (collision). **Collision in bent regular/random rooms is analytic**: `buildWallArcs()` turns each wall into a true circular arc (sagitta = bend × len × 0.3); `firstHitArcs()` solves one quadratic per wall and `computePath` reflects off `arcNormal()` — never reintroduce subdivided-segment collision, it caused both lag (720 segment tests/bounce) and normal-step jitter. The polyline samples the SAME arcs so visuals always match physics. Always change bend through `bendWalls()`, never `buildShape()` (re-randomizes Randomgon). Circle, blob, parabolic, ellipse are exempt (`wallArcs` null → `firstHitPoly`).
- Beam vertex layout is **8 floats**: x, y, t, r, g, b, alpha, edge (cross-beam −1…+1, drives the edge-gradient falloff). `stride = 8*4` and `vertCount/8` must stay in sync with `pushQuad`/`pushShape` writes — grep for all of them if you ever change the layout again.
- New UI labels in the modulation/beat/MIDI/record/glow panels are English-only (no `data-i18n` keys yet); add keys to all four language tables if you internationalize them.
